# Stage 6 report — actions

clean; `runServer` starts and stops cleanly with the pre-existing four-menu `menus.yml`.

## 1. What was built

New in `action/`:

- `Action` is now a sealed interface with one nested record per type: `PlayerCommand`,
  `ConsoleCommand`, `ElevatedCommand(command, permissions)`, `Message`, `OpenMenu`, `Back`,
  `Close`, `Delay(ticks)`. Every switch over it is exhaustive, so a ninth type is a compile
  error at each place that forgot it. `ActionType` is the enum of the eight stored names.
- `ActionParser implements storage.ActionCodec`. `read` takes the explicit stored form (`type`
  required, case-insensitive; `value` for the five that need it; `permissions` list for
  `PLAYER_ELEVATED`, empty allowed; `ticks` for `DELAY`, non-negative integer; unknown keys
  rejected). `write` returns a fresh `LinkedHashMap` and a fresh permissions `ArrayList` every
  call. `parseShorthand` and `parseList` take the prefix form for stage 8. `clampTotalDelay`
  is the list-level cap; `readList` and `parseList` both apply it.
- `ActionExecutor` is the `InventoryClickListener.Dispatcher`. Order on a click: pending
  sequence check, cooldown check and mark, click sound, then the list. `DELAY` suspends the
  walk into a `runTaskLater` task held in a `Map<UUID, BukkitTask>` on the executor. `MENU`,
  `BACK`, `CLOSE` are queued for the next tick; `MENU` checks `maxDepth` first. Elevated
  commands use `addAttachment` and `attachment.remove()` in `finally`. A `PlayerQuitEvent`
  handler on the executor cancels the pending task. The class-head comment explains why it is
  not a loop, why pending state is not session state, and the elevation window.
- `ActionTextResolver` is the stage 9 seam: `Component message(raw, viewer)` and `String
  command(raw, viewer)`. `CommandSanitiser.sanitise` strips newlines, carriage returns,
  semicolons and leading slashes, and the executor applies it to every command string after
  the resolver and before dispatch. `MyMenu` wires `ActionTextResolver.parsingOnly(items::parse)`,
  so `MESSAGE` text gets `&` codes and `<!mm>` now, with no substitution.

New in `service/`: `CooldownStore`, per player, per (menu, slot), in memory, pruned lazily,
not cleared on quit so relogging does not dodge a cooldown.

Changed in `storage/` (the approved widening): `ActionCodec.readList(entries, where)` with a
default that maps `read`, and `MenuYamlFormat.readActions` collects each key's entries and
calls it once. Nothing else in `storage/` changed.

Changed in `MyMenu`: `ActionParser` replaces `ActionCodec.NONE`; `ActionExecutor` is built,
registered as a listener, and wired as the dispatcher. The two config values are hard-wired to
SPEC's defaults through named constants with `TODO(stage 7)` and setters ready.

`InventoryClickListener` was not changed; its `toKey` mapping and list selection were already
what the stage required.

## 4. The two questions

**1. Logout mid-DELAY, rejoin before the delay would have expired.** The quit handler cancels
the task, so nothing resumes on rejoin: the remaining actions never run. That is what should
happen. SPEC §9.2 names logout as the cancellation; the menu context is gone; and a `CONSOLE`
`give` firing at some moment after a fresh login, when the player did not click, is exactly
the kind of surprise that gets reported as duplication or as an exploit. The trap the design
avoids: without an explicit cancel, a task holding the old `Player` object would see
`isOnline()` true after rejoin (it checks by UUID) and would run against a stale entity
handle. Hence cancel on quit rather than "check online on resume"; the online check in
`resume` is only a guard for a quit racing the same tick.

**2. Elevated command that schedules later work.** The attachment is removed when the
`finally` runs, so anything deferred by the command (a confirmation such as `/tpa accept`, a
plugin that queues the work and re-checks permissions when it executes, an asynchronously
executing command) sees the player without the node and behaves as it would for any
unprivileged player. This is intended. The grant covers the synchronous dispatch and nothing
wider; widening it is how 1.x's temporary op became permanent. Commands that need to act
later should be `CONSOLE` actions. Recorded in the executor's class comment.

## 5. The reconcile: `maxDepth` and the 32

Implemented as SPEC §9.3 says: before `navigate`, the executor reads the session's history
size; at or above `maxDepth` (10) it logs a warning and does nothing. The stack therefore
never holds more than ten entries. `NavigationStack.MAX_DEPTH = 32` is unreachable while
`maxDepth` is at most 32 and is now dead code; it should be deleted when `session/` is next
open, and stage 7 should bound the config value at 32 until then (DECISIONS #83).

## Addendum (2026-09-19, after review)

Section 6 above records the behaviour choices as the stage made them, before review. The
review reversed two of them and confirmed one, recorded in DECISIONS #86 with the reasoning:
an empty action list now plays no click sound and starts no cooldown, and a sequence ends as
soon as nothing executable remains, so a trailing `DELAY` no longer holds the player pending.
The rule that a step which throws stops the rest of its list stands. The review also kept
`NavigationStack.MAX_DEPTH` as the hard ceiling and added a clamp in `ActionExecutor.setMaxDepth`
(DECISIONS #83), and answered the changelog note by adding the line. Section 6 is left as written.
